## Findings

1. **The tool does not check a volume name's characters.** The sheet and the plan took `zz_bl45_vol02+`;
   the array refused it at apply (*HTTP 400 code 69, illegal character in input*), after three objects
   were made. `help createvv` on OS 10.6.0: a name up to 255 characters, letters, digits, `.`, `-`, `_`.
   A check on the sheet, as BL-55 does for size, would stop it before any write. Not fixed here.
2. **"WSAPI" on screen.** The failed apply's status line reads *Stopped while creating volume
   zz_bl45_vol02+: WSAPI createVolume zz_bl45_vol02+ failed: illegal character in input (HTTP 400, code
   69, ref name)*. SPEC-030 R10 bans *WSAPI* in operator text; only code 28 (size) has its own sentence,
   other array refusals fall through to the generic wording. Not fixed here.
3. **The as-built calls an iSCSI host zoned.** Its zoning line reads *Zoned on both fabrics:
   zz_is_eljr*. The zoning report puts a logged-in iSCSI host in the provisioning gate's list
   (`zoned_hosts`), and the as-built prints that list under FC words. It should say the host is logged
   in over iSCSI. Not fixed here.

### Fixed afterwards, on this branch (tests on fakes and captures; not yet run live)

1. The sheet refuses a volume name outside the rule of `help createvv`, and the plan blocks one (a new
   volume with such a name is a conflict). Host, host set and volume set names are not checked: no
   captured help states their characters. `lab/failed_apply_lab.py` now checks that the sheet refuses
   `zz_bl45_vol02+`, and makes the apply stop at the volume set `zz_bl45_vvs+` instead, expecting the
   array to refuse a `+` there too (not yet seen live).
2. Array refusals read *Could not create volume x. The array said: illegal character in input (HTTP
   400, code 69, ref name)*; no *WSAPI* and no API call name in any of them.
3. The as-built names an iSCSI host apart: *iSCSI, no zoning needed: zz_is_eljr (logged in on 1:4:1).*
