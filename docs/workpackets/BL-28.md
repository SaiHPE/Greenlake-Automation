## Goal

The first slice is **steps 4–7**: a GET-only v3 client, and a *File service* section in Discovery,
the as-built and two Verify rows (file service state, File ports up). On an array with File ports
they show the file service, its File ports, file systems, client groups and shares. Nothing is
written to any array. No sheet tab, no step, no mode. On an array without File ports nothing
changes. Live on D22U27, plus E18U31, which must show nothing about file.

## Decisions (do not reopen)

- Reads go over the array's **WSAPI v3** (`https://<array>/api/v3`), with the run's one array
  credential (ADR 0013). A new client; do not touch `adapters/array/wsapi_client.py` (v1).
- The v3 client does **GET only**, plus the session login and logout. Any other method raises.
- **The session value:** send the login's body `key` as `X-HP3PAR-WSAPI-SessionKey` **and** the
  three cookies together, as both captures did. A later two-GET probe (one GET with each) narrows
  it; this slice does not. **Always delete the session** (`DELETE /api/v3/credentials/<key>`),
  also when a read fails or raises.
- **A read of another array is refused** (AGENTS rule 4). Each collection's `arraySerialNumber`
  must equal the serial `showsys` prints; when any of the four is missing it or names another,
  nothing from the read is shown, stored or put in the as-built, and Discovery says SPEC-028 R2's
  sentence for it.
- File ports keep coming from `showport -file` through the existing `parse_file_ports`. Do not also
  read them from `/api/v3/ports` (lesson 41: one source per fact).
- New names: `domain/unified_file.py`, `application/unified_file/`, `adapters/array/wsapi_v3_client.py`.
  Not `file`, not `filestorage` (kept for BL-29, deferred). No cloud adapter in this packet.
- No sheet tab, no new step, no new mode in this slice.
- Operator sentences are SPEC-028 R2's, word for word. Any hint that names `controlport config
  file` says plainly that it reboots the array.

## Steps (each passes `scripts/check.py` alone; commit after each)

1. **Capture script.** `lab/file_capture.py` for D22U27 (address as in `lab/iscsi_capture.py`). SSH:
   `showversion`, `showport`, `showport -file`, `help`, `showlicense`. WSAPI v3: `POST
   /api/v3/credentials` with `{"user", "password"}`, then `GET` `/api/v3/fileservice`,
   `/filesystems`, `/filesharesettings`, `/fileshares`, `/ports`, then `DELETE
   /api/v3/credentials/<token>`. Save each answer with its HTTP status, including errors (a 404 is
   a fact). No write call of any kind. Add the README row. *Test:* none (lab is outside the gate);
   `python -m py_compile lab/file_capture.py`.
2. **Fixtures.** The owner runs it; commit the files under `tests/fixtures/unified_file/<TAG>/` with a
   README: OS, WSAPI v3 version if shown, service on/off, counts, which fields came back, and the
   answers to research §8 Q1–Q3, Q6. Remove any session token or cookie value. *If v3 did not
   answer, stop here and tell the owner. (Both arrays answered.)*
3. **Models and parsers.** `domain/unified_file.py` and `application/unified_file/read.py`
   (`parse_*` only; `read_file_report` comes in step 5). Field names exactly as in the capture; a
   field the capture lacks is optional. *Tests:* each parser on the capture; empty collections;
   a share's file system and client group joined by name.
4. **v3 client.** `wsapi_v3_client.py` with `httpx` (a direct dependency, as in
   `adapters/greenlake/http_client.py`), the array's certificate checked against the run's pin as the
   v1 client does (ADR 0026), session from the
   login answer: the body `key` as `X-HP3PAR-WSAPI-SessionKey` and the three cookies, sent together
   on every GET, as both captures did (*Decisions*). **`Content-Type: application/json` on every
   request, GETs included** (OS 10.5.x answers 400 `MISSING_MEDIA_TYPE_HEADER` without it). Logout
   `DELETE /api/v3/credentials/<key>`, always: the context manager's exit runs it after a failed or
   raising read too. Proxy bypass as `_bypass_proxy_for`. `post`, `put`, `patch`, `delete` do not
   exist on the class. *Tests (contract):* login sends the body above; every GET carries the key
   header, the cookies and `Content-Type`; `get` records method, path and status in the command
   log; the password, key and cookie values never appear in the log; a 400/401/404 JSON answer is
   returned as an answer, a connection error raises; logout is sent when a read raises.
5. **Discovery.** `read_file_report(cli, v3, os_version)`: skip entirely when there are no File
   ports and the OS is below 10.5; R2's sentences go to `FileReport.notes`; a v3 failure is a note,
   never a Discovery error. A 401 on the reads after a good login is R2's session note, not a
   failure. The serial check (*Decisions*) reads `showsys` (allowlisted) and refuses a mismatch with
   R2's sentence. Wire into `discover` after `showport -file`. API type and the *File service*
   section in `DiscoveryStep.tsx` (four folded parts, as SPEC-028 R3). *Tests:* the R2 cases,
   including the 401 and the serial refusal (a missing and another serial); rack13 (no File ports,
   service off) → `file is None` although v3 answers; D22U27 → a report.
6. **As-built and Verify.** Section *File service* (service line; ports table; file systems table;
   shares table with clients), read when the document is made with the run's credential; omitted
   when `file is None`. Verify adds two rows (file service state, File ports up). *Tests:* the
   section from the capture; absent without File ports.
7. **Docs.** CONTEXT glossary, SPEC-028 status *R1–R3 built, pending live run*, ARCHITECTURE line,
   SCOPE area 6 (*Partial* once slice 1 is live; it stays *Partial*: service enablement, File port
   mode and snapshots are excluded).

## Risks

- **v1alpha1 churn.** The GreenLake File Storage API is v1alpha1, and HPE's versioning guide says:
  *"No guarantees on backward compatibility."* Only slice 5 would touch it; slices 1 to 3 do not.
- **The wrong session value makes every read 401.** That is R2's session note in Discovery, not a
  failure, and block storage is unaffected. It is why both values are sent until the probe.
- **Port mode reboots the array.** `controlport config file` needs `-sysreboot`. The tool never
  sends it, and any hint that names it says plainly that the array reboots.
