### G-0 — what the provisioned as-built needs (design note)

Read-only, from the array the step already logs into, plus the run's own records. New template
sections after *checkhealth* (matched by intent like the existing three, never by exact string):

| Section | Source | Content |
|---|---|---|
| **Hosts** | `showhost -d` (+ `showhost -persona`) | one row per host: name, persona, WWPNs/IQNs, ports logged in, host set membership. Unclaimed logins listed separately as "logged in, no host object". |
| **Host sets** | `showhostset` | name → members |
| **Volumes** | `showvv -showcols Name,Prov,CPG,VSize_MB,UsrCPG,Comment` + `showvv -s` | name, type (tpvv/reduce), CPG, size, used; VV-set membership from `showvvset` |
| **Presentations (exports)** | `showvlun -t` | one row per template: source (volume or set), target (host or set), LUN, type. State per port from `showvlun -a` summarised as "N of M ports active". |
| **SAN zoning** | the run's `zoning.plan` event + `zoning.previewed` report | per fabric: switch, fabric name, active cfg; per host HBA port: array ports zoned to, zone name(s); the command set the tool handed to the SAN team, verbatim, marked "applied by SAN team — confirm" until a re-check shows the login. |
| **Path verification** | the run's `storage.paths.verified` event | per host: HBAs live, fabrics, LUN count |
| **Provisioning record** | the run's `storage.applied` event | what this run created vs. what already existed, with timestamps — the difference between "the array's state" and "what we did" |

Scope rule for the document: the array sections describe **everything on the array** (a customer
hands over the array, not the run); the run sections describe **what this engagement did**. Both
are needed, and the as-built warnings list must say when a section is empty because the array has
nothing, not because the read failed.
