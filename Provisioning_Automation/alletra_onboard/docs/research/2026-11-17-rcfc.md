## 2. The commands, from the array's own help

The `creatercopytarget`, `admitrcopylink` and `dismissrcopylink` help is the same on Alletra MP OS
10.5.0, 10.5.55 and Primera OS 4.6.20. The `controlport` lines for `config`, `rcfc`, `offline` and `rst`
are the same on those three and on OS 10.6.0 (its differences are in the `rcip`, `file`, `nvme` and
`rate` text only).

**Port mode.** `controlport` help:

- `controlport config <connmode> [-ct <ctval>] [-unique_nwwn enable|disable] [-virt_ports <num_virt_ports>] [-f] [-sysreboot] <node:slot:port>...`
- `<connmode>`: *"Specifies whether the port is used for a disk, host, peer, Remote Copy over Fibre
  Channel (rcfc) or iSCSI (iscsi) …"*; *"if <connmode> is "rcfc", then <ctval> can only be "point"."*
- Its example: `controlport config rcfc 0:0:1` (no `-ct`, no `-f`, no `offline` before it).
- *"Controlport config mode changes are not allowed when ports are online."*
- `controlport offline <node:slot:port>...` *"Holds the specified port offline indefinitely. Issue
  controlport rst to bring the port back online."*

So one FC port has one connection mode: `host`, `disk`, `peer` or `rcfc`. RCFC and peer ports
(BL-26, migration) compete for the same free FC ports.

**The Remote Copy interface on the port.**

- `controlport rcfc init [-f] <node:slot:port>`: *"Sets the specified Remote Copy interface on the
  local port. Only for RCFC ports."*
- `controlport rcfc delete [-f] <node:slot:port>`: *"Deletes the configuration for the Remote Copy
  interface on the local port. This will bring the interfaces down."*
- *"The controlport rcip and controlport rcfc commands are required for setting up Remote Copy interfaces."*

**The target and its links.**

- `creatercopytarget [options] <target_name> FC <node_WWN> [node:slot:port:WWN...]`; `<node_WWN>`:
  *"The node's World Wide Name (WWN) on the target system (Fibre channel target only)"*; each link is
  *"the node, slot, and port of the FC port on the local system and World Wide Name (WWN) of the peer
  port on the target system"*. Example: `creatercopytarget System2 FC 20010002AC000060 0:4:1:22410002AC000060 1:4:1:23410002AC000060`.
- `admitrcopylink <target_name> <N:S:P:WWN>...` and `dismissrcopylink <target_name> <node:slot:port:WWN>...`;
  *"The transport layer (RCIP or RCFC) is set using the creatercopytarget command."*
- `removercopytarget [options] <target_name>`: unchanged from RCIP.

**Reads.** `showrctransport -rcfc` *"Show information about Fibre Channel end-to-end transport"*;
`showport -rcfc` *"information that is specific to the Fibre Channel Remote Copy ports"*; `showport -rc`
(its 10.6.0 example lists `0:3:3 ready 20330002AC07E903 32Gbps rcfc` beside `rcip` rows);
`showport -c` *"Displays all devices connected to the port. Such devices include … ports from other
storage system (for RCFC and peer ports)"*. All are already allowed by the read client (it checks the
first word: `showport`, `showrctransport`, `showportdev`). **The output of `showport -rcfc` and
`showrctransport -rcfc` has never been captured: unconfirmed: capture on the lab.**

**Not confirmed by any capture:**

- The order of `controlport rcfc init`, zoning and `creatercopytarget`. The help gives the commands,
  not the order. The CLI guide ED8 has it (owner).
- Whether `controlport config rcfc -ct point -f` brings the port back by itself or needs
  `controlport rst` (the same open question as peer ports, ADR 0018 on the BL-26 branch).
- Whether `checkrclink` measures an RCFC link. Its help was never captured; SPEC-020 names an
  `-fcip` option only as a non-goal. **Capture `help checkrclink`.**
- Whether a port's WWN changes when it becomes RCFC. Peer ports do take new WWNs (`0202` in bytes 3–4
  on E18U31, where host ports read `0002`). For RCFC two things point the other way: the 10.6.0 help's
  `showport -rc` example prints RCFC ports with `0002` WWNs, and the Primera's 2026-11-03 FC target
  addressed rack13's ports by their `0002` (host-pattern) WWNs. Neither is a before-and-after read of
  one port.

## 3. The procedure the tool would follow (proposed, order to confirm)

Per array, for each of two FC ports on two different nodes:

```
A, B   controlport offline <nsp>                         port must be offline for a mode change (help)
A, B   controlport config rcfc -ct point -f <nsp>        rcfc takes point only (help)
A, B   controlport rst <nsp>                             only if the port stays offline (unconfirmed)
SAN    zones: A's RCFC port <-> B's RCFC port, one to one   command set for the SAN team (ADR 0012)
A, B   controlport rcfc init -f <nsp>                    the Remote Copy interface (help); order unconfirmed
A, B   startrcopy                                        when Remote Copy is not started (as SPEC-021)
A      creatercopytarget <B> FC <B node WWN> <A nsp>:<B port WWN> <A nsp>:<B port WWN>
B      creatercopytarget <A> FC <A node WWN> <B nsp>:<A port WWN> <B nsp>:<A port WWN>
verify showrcopy links (Up) · showport -rcfc · showrctransport -rcfc · showport -c
undo   removercopytarget <name> · controlport rcfc delete -f <nsp> · port back to its old connmode
       (controlport offline, controlport config host -ct point -f, rst if needed) · zones out (SAN team)
```

The zones pair one local RCFC port with one remote RCFC port, node to node. That is what the lab's own
zones look like (§4: `rcfc1` = Primera 0:3:2 with rack13 0:3:4; `rcfc2` = Primera 1:3:2 with rack13
1:3:3) and what ADR 0004 recorded from the 3PAR user group ("they get their own RCFC↔RCFC zones").

## 4. The lab: is there an RCFC path between rack13-ARCUS and the Primera 630 today?

**No, not as rack13 sees it on 2026-11-16.**

1. **The one login on 0:3:4 and on 1:3:3 is an ESXi host, not the Primera.** `showportdev ns 0:3:4`
   and `showportdev ns 1:3:3` list port WWN `10005CED8C5312A9`, node `20005CED8C5312A9`, SNN
   *"Emulex SN1720E2P … HN:DL380G10R13U25… OS:VMware ESXi 8"*, plus rack13's own ports and their NVMe
   virtual ports. `showhost -d` shows `10005CED8C5312A9` as an unclaimed login on both ports. On
   2026-09-12 that WWPN was the F1 HBA of ESXi host 10.132.30.136 (validation record).
2. **No Primera WWN appears on any rack13 port.** The Primera's node WWN is `2FF70002AC02AC38`; its
   RCFC-labelled ports are `20320002AC02AC38` (0:3:2) and `21320002AC02AC38` (1:3:2). None is in any of
   the eight `showportdev ns` files. For comparison, another array in a port's view looks like
   E18U31's peer port 0:3:2: *"HPE_3PAR 20850_R2 - 4UW0002142 - fw:3313"*, node `2FF70002AC07E528`.
   The view is zone-filtered and lists every logged-in member of the port's zones (it lists the ESXi
   HBA and rack13's 1:3:3, the members of zone `kiranzone1`). So either `rcfc1`/`rcfc2` are no longer
   in F1's effective configuration, or the Primera's 0:3:2/1:3:2 are not logged in on F1. rack13's
   capture cannot tell which.
3. **No rack13 FC port is in RCFC mode.** `showport -par`: every FC port `host point`. `showport`:
   every FC port mode `target`. An RCFC link needs an RCFC port at both ends, so even with the zones
   active no link could come up without changing two rack13 ports.
4. **Cabling.** Only 0:3:3, 0:3:4, 1:3:3 and 1:3:4 have SFPs and a link (32 Gbps, `fabric`); 0:3:1,
   0:3:2, 1:3:1, 1:3:2 have none (`loss_sync`, `showportdev`: *Unable to get device list*). 0:3:3 and
   1:3:4 are `ready` and Type `free` but see nothing at all (`0 total`, not even themselves): linked to
   a switch, in no active zone (inference).

**How it got here (history, from the fixtures).**

- 2026-09-12: F1 (`SAN6700R13U38`, fabric `Training_Lab_Rack12`) effective config `mycfg` held
  `rcfc1` (`20:32:00:02:ac:02:ac:38; 20:34:00:02:ac:02:d4:95`) and `rcfc2` (`21:32:…ac:38;
  21:33:…d4:95`); F2's `jul2prabhu` held `primera_arcus_rcfc1/2` with the same members, although
  rack13's 0:3:4 and 1:3:3 were on F1. F1's `nscamshow` listed the Primera's 0:3:2 and 1:3:2 on the
  remote switch `SN6000B-SANB-ZR07U40` as *"Physical Target"*, FC4 *Target*, 16G. Both ends were
  host-mode target ports: the zones existed, an RCFC link could not.
- 2026-09-28: F1 `cfgactvshow`: *"No Effective configuration: (No Access)"*.
- 2026-11-03: the Primera's 0:3:2 and 1:3:2 read `initiator ready … free FC RCFC`. It held an FC
  target `rack13-ARCUS_PRIMERA`, status `failed`, Options `2FF70002AC02D495` (rack13's node WWN), links
  `0:3:2 20330002AC02D495` and `1:3:2 21340002AC02D495` Down (rack13's 0:3:3 and 1:3:4: not the ports in
  the zones), `receive` rows Up, and five Stopped sync groups, last sync 2026-10-19 08:09:50 IST, three
  named `.r185493` (rack13's system ID). rack13 said *"Remote Copy is not configured on this system"*.
  So an RCFC partnership between the two existed before 2026-10-19. That target and its groups were
  removed the same day (`removercopytarget -cleargroups -f`, validation record 2026-11-03, LESSONS 44).
- 2026-11-16: rack13 upgraded to 10.6.0; the state in points 1–4.

**What a lab RCFC pair would need** (owner and lab team, not the tool):

- Two rack13 FC ports in RCFC mode. The only free linked ones are 0:3:3 and 1:3:4 (two nodes, both on F2
  as cabled on 2026-09-12). 0:3:4 and 1:3:3 are the ports the old zones name, but they carry the ESXi
  login; changing them takes that HBA's paths away (no export uses them today: `showvlun -a` lists only
  iSCSI paths).
- The Primera's RCFC ports on the same fabric as rack13's chosen ports, with one-to-one zones.
- Read-only captures first (§7).

The other lab arrays cannot carry RCFC without taking host ports: E18U31's 0:3:2/1:3:2 are peer ports
and its free 0:3:3/1:3:3 have no SFP; D22U27 has one free linked FC port (0:3:2); VZ's free FC ports are
`loss_sync`.

## 6. What breaks today on an existing RCFC partnership

The group calls are transport-free: WSAPI `/remotecopygroups` takes a `targetName`, nothing else
(apply, verify and the failover test need no change). Everything that finds, checks or describes the
partnership assumes IP:

| # | Where | What happens with RCFC |
|---|---|---|
| 1 | `application/replication/plan.py` `_targets_towards`, `find_partnership` | match a target only when its links point at the other array's **RCIP addresses**; with no RCIP address on the other side they return nothing. An RCFC partnership is never found. |
| 2 | `plan.py` `check()` | so the step blocks: *"No Remote Copy partnership … RCIP addresses …"* plus *"Remote Copy over Fibre Channel target(s) found (…); this tool supports Remote Copy over IP only."* |
| 3 | `domain/replication.py` `RTT_LIMIT_MS` and `check()` | one table, RCIP values (async 200 ms). RCFC is 10 ms for both modes: an async row with a typed 50 ms would pass. The sentence says "over RCIP". |
| 4 | `application/replication/partnership.py` `stale_fc_targets` | when the workbook has a Replication network tab, **any** FC target that carries the other array's node WWN is a blocker that tells the operator to run `removercopytarget -cleargroups -f`, whatever its status. On a working RCFC pair that sentence would remove a live partnership and its groups. It was written for the failed target of 2026-11-03. **Fixed by BL-57** (§11). |
| 5 | `read.py` `parse_showport_roles` | keeps the node WWN of the **first** FC row and drops each port's WWN. FC links are addressed by port WWN, and on an array with a peer port listed first the node WWN would be the peer port's `0202` one. |
| 6 | `read.py` `read_array` | reads `showrctransport -rcip` only. |
| 7 | `application/replication/steps.py` `_gate_on_link` | once any partnership is found, demands an RCIP link check; text "over RCIP". |
| 8 | `application/replication/link_check.py` `plan_pairs` | RCIP only. Says the FC sentence only when this array has no RCIP port at all; otherwise every FC link is "has no RCIP address". |
| 9 | `frontend/src/steps/ReplicationStep.tsx` | `const rcip = !!report?.partnership`: any partnership shows *Check the link*; the limits panel says "over RCIP"; the array card lists RCIP ports only. |
| 10 | `application/documents/asbuilt.py` | partner table column *RCIP ports*; "Found by link address"; link-check paragraph "over RCIP". |
| 11 | `adapters/array/rc_cli_client.py` | (setup only) `creatercopytarget … IP` only; `admitrcopylink` / `dismissrcopylink` accept `N:S:P:IPv4` only; `controlport` rcip forms only. |
| 12 | `application/provisioning/discovery.py` `parse_ports`, `zoning_plan.py` | (setup only) target-mode ports only, and a zone is always host × array. An RCFC zone is array × array: the same block BL-26 (step 7) designs for peer ports. |
| 13 | `application/platform/init_sheet.py` Replication network tab | (setup only) address, netmask, gateway per port; an RCFC port has none of these. |
| 14 | `adapters/array/wsapi_client.py` port maps | WSAPI port type 5 (RCFC in python-3parclient) is not mapped; matters only if a WSAPI port read is used. |

## 7. Latency

Support Matrix (research 2026-10-07 §3, OS 10.5 column): synchronous ≤ 10 ms on RCIP, RCFC and FCIP;
asynchronous periodic ≤ 200 ms RCIP, **10 ms RCFC**, 120 ms FCIP. An RCFC link stretched over FCIP
routers looks like RCFC to the array; the tool cannot see the routers, so only the engineer can say
"FCIP". Whether the 120 ms FCIP limit applies to such a link from the array's side is unconfirmed.

`checkrclink` on RCFC is unconfirmed (§2). Until it is captured, the only latency the tool has for an
RCFC pair is the number typed on the Replication tab.

## 8. DSCC: a REST path the earlier research did not look at

ADR 0015 *Context* says the DSCC API's `replication-partners` is GET-only. That is true of the
**block-storage** API it read. The **storage-fleet** API (v1alpha1, mirror scraped 2026-06-07) has:

- `POST /storage-fleet/v1alpha1/devtype4-storage-systems/{systemId}/replication-partners`: *"Create
  replication partners"*; `source.type` *"1 for IP Target Type, 2 for FC Target Type"*, `source.nodeWwn`
  *"WWN of the node on the target system for FC Link type"*, `portPosAndLink[].link` *"If the Link
  Protocol Type is FC, specify the WWN of the peer port"*, and a `target` body for the other side.
  Also `PUT …/replication-partners/{id}` and `POST …/replication-partners/remove`.
- `PUT /storage-fleet/v1alpha1/devtype4-storage-systems/{systemId}/ports/{id}/fc`: `configMode`
  *"Possible Values: Disk, Host, RCFC, Peer"*, `connectionType` *"Point, Loop"*; answers 202 with a task.

The live v1 API, read later the same day, is in §11; it supersedes this reading for ADR 0024 option C.
Nothing here was probed. It needs a DSCC API client with write scope (the tool has none; SCOPE lists
our DSCC workspace entitlements as unknown), both arrays in DSCC, and the peer may not be a
`devtype4` system (the lab peer is a Primera). It is a real alternative for ADR 0024 and for ADR 0018
(peer ports), not a recommendation.

## 9. Recommendation

1. **First slice: an existing RCFC partnership, read-only detection first** (SPEC-031 part A). Find the
   partnership by WWN, name the transport everywhere, apply the RCFC limits, stop the SPEC-021 blocker
   from ever offering to remove a working FC target, and let the groups, verify, failover test and
   as-built run over it. No new write; no allowlist change. It can be unit-tested on the Primera's
   2026-11-03 FC target, but it can only be proven live on a working RCFC pair, which the lab does not
   have today.
2. **Second slice: the tool sets RCFC up** (SPEC-031 part B), after ADR 0024 is decided, the CLI guide's
   order is confirmed and the lab has a pair to try it on. It needs new command forms on the
   write-scoped client and a port-mode change (the owner's decision), and the apply splits in two
   around the SAN team's paste of the zones.
