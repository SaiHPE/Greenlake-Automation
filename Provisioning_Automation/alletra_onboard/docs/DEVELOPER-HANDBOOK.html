1. The problem we solve

When a customer buys an HPE Alletra Storage MP B10000 array, an HPE field engineer goes to the customer's data centre to make it work. That takes a day or two and has many small steps, each on a different system: register the array in HPE GreenLake, connect it to the cloud through a setup page on the array itself, finish the setup in the Data Services Cloud Console (DSCC), find out which servers are cabled to which switch, write the zoning for the SAN team, create the volumes and present them to the servers, set up replication to a second array if the customer bought one, check that everything matches what was ordered, and write the hand-over document.

Each of those steps is well understood, and each is easy to get slightly wrong by hand. A typo in a port address, a volume exported to the wrong host, a zoning command pasted into the wrong fabric. The engineer also has to write the as-built document afterwards, by hand, from memory and screenshots.

This tool does that day for the engineer. It is a small web application that runs on the Windows "jump box", the laptop or server that sits next to the array in the customer's network. The engineer fills in one spreadsheet, uploads it, chooses what they want to do, and walks through the steps one at a time. The tool reads the real environment, shows the engineer exactly what it is about to change, waits for a yes, does it, checks the result, and writes the document.

Who uses it: HPE deployment engineers, on site, one array at a time. They are storage experts, not developers. The screens talk to them in plain words, and every screen says what the tool found, what it means, and what to do next.

2. The tool in one picture

Technically the tool is one Python program (built with FastAPI) listening on 127.0.0.1:8765. It serves a web page, built with React and HPE's design system, and an API that the page calls. The same program talks to the outside world on the engineer's behalf. Nothing else is involved: no server in the cloud, no database service, no login. The engineer is the only user, and the program runs only on their machine.

Three words you will meet in every file:

Run
One array, one chosen set of steps, and the full history of what happened. Everything the tool does is inside a run.
Step
One screen and one job: Discovery, SAN Zoning, Provision storage, and so on. The engineer presses a button; the step does its work and reports back.
Event
One line in a run's history: "discovery finished, here is the report". The screen is drawn from events, so a refresh or a restart loses nothing.

3. What the tool never does

These are not preferences. Each came from a real risk or a real incident, and each is checked in code review. A change that breaks one of them will not be merged.

RuleWhy
It never writes to a SAN switch. It produces the Brocade commands as text for the SAN team to paste.A wrong zone can cut a customer's production servers off from their storage. Zoning changes belong to the people who own the switches and the change window. (Decision record ADR 0012.)
It reads the array over SSH with a fixed list of allowed commands, all of them "show" commands. It writes to the array only through the array's REST API, and only after the engineer has seen the plan and ticked a box.Every change to a customer's array must be something the engineer saw and agreed to. The fixed list makes it impossible for a bug to send a destructive command. (ADR 0001.)
Discovery, verification, the path check and the as-built document only read.They run against live customer systems to report, so they must be safe to run at any time.
One array per run. A spreadsheet that names two arrays is refused.Credentials, plans and documents belong to one array. Mixing two is how the wrong array gets changed.
No passwords, customer names or customer addresses in the repository, in test data or in screenshots. Lab addresses are fine.The repository is shared across the team, and part of it is pushed to a public site for lab runs.
Nothing is "done" until it has run on real lab hardware.Most of our bugs passed every automated test and failed on a real array, because real devices answer differently from their documentation.

You need git, Python 3.12 or newer, Node 20 and GitHub's command line tool gh. On Windows, also Git Bash, which comes with Git for Windows. Then, in a terminal:

On a Windows laptop, replace .venv/bin/python with .venv\Scripts\python everywhere on this page.

If pip or npm complain about certificates HPE's network inspects encrypted traffic, which confuses tools that ship their own certificate list. On a Mac, export the trusted certificates once and tell the tools where they are: 
security find-certificate -a -p /Library/Keychains/System.keychain \
  /System/Library/Keychains/SystemRootCertificates.keychain > ~/hpe-ca.pem
export PIP_CERT=~/hpe-ca.pem NODE_EXTRA_CA_CERTS=~/hpe-ca.pem

Reading the code: your first afternoon

Six files, in this order, about two hours. Paths are under src/alletra_onboard/. Read sections 14 to 17 of this page alongside them.

  1. domain/workflow.py (100 lines). The ten steps, the five preset modes, and the three functions that pick steps for a run. Notice that nothing else in the code lists steps.
  2. domain/models.py (300 lines). WorkflowPhase, RunMode, RunStatus, then ArrayWorkItem, RunEvent and RunRecord. Notice that a step has one key but may pass through several phases; GreenLake registration has six.
  3. application/runs/coordinator.py (290 lines). Read create_run, then spawn, _guarded, set_state and emit. This is the whole run machinery. Notice spawn refuses a second task for the same run, and that emit writes to the store before it tells the browser.
  4. application/provisioning/steps.py (400 lines). Two step services. Read start_discover and _run_discover first; every other step has that shape. Then start_storage_apply, to see how an approval is checked and withdrawn.
  5. application/provisioning/storage_provision.py (760 lines). Skim. build_plan judges each object; apply_plan walks the ensure_* calls; removal_set renders the undo. Notice that these are plain functions over models, with the device clients passed in.
  6. api/app.py (780 lines). Skim the routes. Notice how little each one does, and how the four exceptions are mapped to 404 and 409 in one place.

After that, follow one feature end to end with the frontend open: frontend/src/steps/ProvisionStep.tsx next to ProvisioningSteps. When you can say what each button sends, what event comes back and which component reads it, you can work on any step.

How we work

8. From an issue to a merged change

Every change follows the same path. Nothing goes straight to main; github.hpe.com refuses it. The path has three lanes: you, GitHub, and the owner.

  1. Pick an issue. Labels show the area (area/replication, area/docs, …) and the state (build, needs live run, blocked, in progress). Assign it to yourself. For anything large, write a few lines in the issue about how you plan to do it before you start, so the owner can steer early. If there is no issue for what you want to do, open one; its title starts with the next free BL-NN number (the list is in docs/TRACKER.md).
  2. Branch from an up-to-date main: git switch main && git pull && git switch -c feat/bl-NN-short-name. One issue per branch.
  3. Make the change. Code and tests together. Update any document that describes the behaviour you changed, including this page: if a section here is now wrong, fix it in the same pull request. Commit as often as you like; the merge squashes it to one commit.
  4. Run scripts/check.py until it ends with PASS (section 9).
  5. Push and open the pull request on github.hpe.com (section 10).
  6. github.hpe.com checks the rules: the change must come through a pull request, and the owner must approve it. A push after approval needs approval again.
  7. Review. The owner reads it and comments. Answer each comment, push, and ask for another look.
  8. Squash and merge. The owner merges. Your commits become one commit on main with the pull request's title as its message, your branch is deleted, and Closes #N in the description closes the issue.
  9. After the merge the owner runs one script that rebuilds the screens and refreshes everything downstream (section 13).

If your change reaches an array, a switch, vCenter or GreenLake, it also needs a run on the lab (section 12). Until then the issue keeps the needs live run label.

12. Running on the lab

Do this when your change reaches an array, a switch, vCenter, a host or GreenLake. Book the lab with the team first. Only one person can run at a time: two runs would fight over the same arrays and the same port on the jump box.

  1. Once per jump box. In PowerShell on labrat, put the lab passwords in the app's .env. The lab scripts read them from there, so they never prompt and the passwords are never in git. 
    cd $env:USERPROFILE\Downloads\alletra_onboard
Add-Content .env "`nLAB_ARRAY_PW=<the lab arrays' 3paradm password>"
Add-Content .env "LAB_DEFAULT_PW=<the lab vCenter and switch password>"
  2. Once per laptop. gh auth login --hostname github.com && gh auth setup-git --hostname github.com.
  3. Each run, on your laptop. Commit your work, then from the repository root (Git Bash on Windows): 
    Provisioning_Automation/alletra_onboard/scripts/push_jumpbox_test.sh
    It builds the screens from your frontend/src, packs the app folder with them, and pushes that to jumpbox-test on github.com. It never changes your own branch.
  4. Each run, on labrat. One paste. Pick the script from lab/README.md: 
    cd $env:USERPROFILE\Downloads\alletra_onboard; git fetch origin jumpbox-test; git reset --hard origin/jumpbox-test; .\.venv\Scripts\python.exe lab\ui_live_lab.py

  5. When you are done, put the jump box back on released code: run the push script from an up-to-date main, then the same paste without the last command.

Read a lab script's header before you run it; it says what it changes on the arrays. Scripts that create things give them names starting with zz_ and remove them at the end. If you write a new one, follow lab/README.md.

13. After a merge, and releases

You do not need to do any of this, but you will see it happen.

After merging, the owner runs scripts/after_merge.sh. It pulls main, rebuilds the screens from frontend/src and commits them if they changed, refreshes jumpbox-package, and refreshes the rolling "latest" download zip on github.hpe.com. That is how your change reaches the engineers.

Numbered releases (v0.17.0 and so on) are also made by hand. The owner tags main, and on a Windows laptop on the VPN runs scripts/publish_release.ps1 -Tag vX.Y.Z -BuildExe. It builds three Windows .exe bundles (one that uses the installed browser, one with a browser inside, one with only the onboarding steps), runs a self-test and a smoke test on each, and attaches them to the release. The script refuses if the tag is not on github.hpe.com or the checkout is not the tagged code.

14. The four layers

Where this fits: the backend box in section 2, opened up.

15. A run

Where this fits: the spreadsheet and the arrow into the tool, in section 1.

A run starts with the spreadsheet and ends with the hand-over document. Here is how it comes into being.

  1. The engineer uploads the spreadsheet. platform/init_sheet.py reads it. The workbook copies HPE's official initialisation worksheet so engineers recognise it, and has six tabs: Initialisation, Provisioning, Volumes, Host sets, Hosts and Replication. Parsing gives two objects. ArrayWorkItem holds the array's identity, its network settings and the GreenLake and DSCC details. ProvisioningIntent holds the array and target credentials (vCenter, the two switches), the hosts, volumes and host sets to create, and the replication rows (peer array, which volume sets, which mode). If the workbook names two different arrays in two places, it is refused.
  2. The parsed sheet waits on the server. It is stored under a one-time token, and the browser gets only the token and a summary with the passwords blanked. Device passwords never go back to the browser.
  3. The engineer picks a mode, and POST /runs/from-sheet turns the token into a run. The token is used up. From here on, every step reads what it needs from the run.

Modes and the step registry

The mode decides which steps the run has. The list of steps exists in exactly one place, domain/workflow.py. The screens read it from GET /app/profile, so the frontend never has its own copy. Adding a step means adding it there, then giving it a service method, a route and a screen.

What the status means

The status is one value for the whole run, not one per step. It answers "is anything happening, and is the engineer needed".

StatusMeaningWhat the engineer can do

Keys and phases are different things, and events carry the phase. A step key (greenlake, provision) is what the engineer selects and what the screen renders. A phase (GL_REGISTER_DEVICE, STORAGE_PROVISION) is where the run is, and it is what current_phase and every event record. Most steps have one phase. GreenLake registration has six, one per sub-step, so its progress reads sensibly in the event list. The registry in domain/workflow.py says which phase a step lands on, and that is how a run that was closed mid-way reopens on the right screen.

16. What happens when you press a button

Where this fits: inside any one step box in section 1.

Every step works the same way, so this one sequence explains most of the application layer. Take "Create storage objects" on the Provision storage screen as the example.

  1. The route calls one method on the service. application/service.py is a thin front door. It holds the RunCoordinator and five step services (OnboardingSteps, DiscoveryZoningSteps, ProvisioningSteps, ReplicationSteps, DocumentSteps) and passes each call to the right one.
  2. The step service checks its preconditions. If they fail it raises StepPreconditionError with a sentence an engineer can read, and the route returns HTTP 409 with that sentence. Examples: zoning before discovery; apply without a previewed plan; a plan with conflicts.
  3. The coordinator starts the work in the background (spawn). There is one background task per run at a time. A second button press while one is running gets RunBusyError, also a 409. That is why the screen never has two things running at once.
  4. The device work runs in a thread. The libraries that talk to the array, vCenter and the switches are blocking, so they are moved off the web server's event loop with asyncio.to_thread. The screen stays responsive.
  5. Results and progress are events. The step calls coordinator.emit(run_id, phase, event_type, message, data). Long steps emit phase.progress lines as they go. The run's status is set separately with set_state: RUNNING at the start; READY, WAITING_FOR_OPERATOR or RETRYABLE_FAILURE at the end.
  6. A crash cannot leave a run stuck. The task runs inside a guard. An unexpected exception becomes a step.crashed event and a retryable failure, so the screen never shows "running" for ever.
  7. Every device command is recorded. When the task starts, the coordinator attaches a recorder to it. Each adapter calls command_log.record(...) after every command, with the secrets it knows about blanked. That log is the Console tab the engineer sees under each step.
# application/provisioning/steps.py, shortened. Every step has this shape.
def start_storage_apply(self, run_id):
    run = coord.get_run(run_id)
    plan = self._previewed_plan(run_id)                              # 2. preconditions
    if plan is None:
        raise StepPreconditionError("no provisioning plan to apply — run the preview first")
    if plan.blockers:
        raise StepPreconditionError("the plan has conflicts that must be resolved on the array first: ...")
    coord.spawn(run_id, self._run_storage_apply(run, intent, discovery))   # 3. background
    return run

async def _run_storage_apply(self, run, intent, discovery):
    coord.set_state(run, RunStatus.RUNNING, WorkflowPhase.STORAGE_PROVISION)
    coord.emit(run.run_id, phase, "storage.apply.started", "Creating host, volumes and exports…")
    result = await asyncio.to_thread(storage_provision.apply_plan, intent, discovery, ...)   # 4. thread
    coord.set_state(run, RunStatus.RETRYABLE_FAILURE if result.error else RunStatus.READY, phase)
    coord.emit(run.run_id, phase, "storage.apply.failed" if result.error else "storage.applied",
               result.error or summary, data={"result": result.model_dump(mode="json")})   # 5. event

17. How the screen knows what happened

Where this fits: the "live events" arrow from the backend to the browser in section 2.

Events are the record, not a side channel. Each one has the run id, the phase, a type such as storage.applied, a message written for the engineer, a data payload (the report, the plan, the result) and a time. When a step emits one, two things happen: it is appended to the run_events table in the local database, and it is pushed to every open browser tab over Server-Sent Events, a long-lived HTTP response on GET /runs/{id}/stream that the browser listens to.

The screen is drawn from the events alone. The newest storage.previewed event is the plan on screen; a storage.applied newer than that preview is the result; a step.crashed or *.failed marks the step as failed. When you refresh the page, or restart the backend, the browser replays GET /runs/{id}/events and the screen is exactly as it was.

One event, as the browser receives it on the stream. Each frame is one line starting with data: and a blank line; the backend sends : heartbeat on its own every few seconds so proxies keep the connection open.

data: {"event_id": "6f1c…", "run_id": "a9d2…", "phase": "STORAGE_PROVISION",
       "event_type": "storage.applied",
       "message": "Provisioning complete — 5 created, 0 updated, 2 already existed.",
       "data": {"result": {"outcomes": [{"kind": "host", "name": "esx01", "status": "created"}, …],
                           "removal": ["removevlun -f vol01 1 set:web", …], "error": null}},
       "created_at": "2026-10-16T09:14:02+00:00"}

The model is RunEvent in domain/models.py; the frontend type that mirrors it is in frontend/src/api.ts. The data payload is whatever the step's result model dumps to JSON, so the TypeScript side reads the same field names you see in the Python model.

StepEvents it emits

18. Changing an array: plan, approve, apply

Where this fits: the Provision and Replicate boxes in section 1, the only two that change the array.

Both of them, and any write we add later, follow the same four stages.

  1. Plan. build_plan() reads the array and compares it with what the spreadsheet asks for. Every object is marked create (not there), exists (there, and the same), update (there, apply will add to it) or conflict (same name, different attributes, which apply cannot fix). Conflicts become blockers. The plan goes out as a storage.previewed event.
  2. Approve. The screen shows the plan as a table and a tick box with the sentence "I have reviewed this plan and authorise creating these objects on the array." The Create button only works once the box is ticked.
  3. Apply checks the approval again. The previewed plan is kept in memory only, paired with the exact discovery it was built from. It is dropped if discovery is re-run or the composition is edited, and it never survives a restart, because an approval is a decision about one specific situation and must not outlive it. A plan with blockers is refused. Replication adds one more condition: the link check must have run first. Then the writes go through the array's REST API. Every create looks before it creates, or accepts the array's "already exists" answer, so running apply twice reports "exists" instead of failing.
  4. Apply returns a removal set. The exact commands that would undo what it created, in the right order: exports, then sets, then volumes, then host sets, then hosts. The tool never runs them. They are shown to the engineer with a copy button and written into the as-built document.

The REST client is adapters/array/wsapi_client.py, a wrapper around HPE's python-3parclient library (version 4.2.14 or newer; older versions call the wrong login path on this array). Logging in is also the readiness check: an array that is still starting up answers 503, and the tool stops there instead of guessing.

Replication and the failover test

Remote Copy is the array's replication feature. It has three layers: the network ports and addresses, the partnership between two arrays (targets and links), and the groups of volumes being replicated. Today the tool reads all three and writes the third.

ModuleWhat it does
replication/read.pyReads one array's Remote Copy state over SSH into a ReplicationArrayView. Every parser is checked against real captures from the lab pair in tests/fixtures/rc_pair/.
replication/plan.pyFrom both arrays' views and the sheet's Replication tab: the blocking findings (no partnership, links down, a pool missing on the peer, a volume already in a group) and the plan (groups to create, volumes to add, what already exists).
replication/link_check.pyRuns checkrclink between the two arrays and reads the latency. Synchronous replication has a latency limit; above it the engineer decides whether to go on. Apply is refused until this has run.
replication/apply.pyCreates the group, sets its mode, adds each volume (which creates the copy on the peer), starts it. All through the REST API. Returns a removal set for each array.
replication/verify.pyReads both arrays again: links up, each group started with the right role on each side, volumes in sync. It never retries a write; it names the HPE procedure to follow instead.
replication/failover.pyThe failover test: stop the group, fail over to the peer, recover, restore, through the REST API's disaster-recovery actions, watching the roles and sync state and timing each leg. The record goes into the as-built.

Verify and the as-built document

DocumentSteps runs the two read-only steps at the end of every mode. Both run after the outcome of the run is decided and never change the run's status: a failed check cannot undo a successful onboarding.

  • Verify configuration (documents/verification.py) logs in over SSH and compares what the array runs (system name, management address, netmask, gateway, DNS, NTP, time zone, and so on) with what the sheet asked for, field by field. Then it adds the array's own status check (checkhealth) and inventory.
  • As-built document (documents/asbuilt.py, asbuilt_parse.py, asbuilt_docx.py) reads the array, parses the tables, and fills HPE's Word template with python-docx, keeping the template's boilerplate: configuration and inventory, what this run created and how to remove it, the zoning command set, the replication groups, the link check and the failover test. The file is saved with the run and served by GET /runs/{id}/asbuilt/download.

Platform

application/platform/ is what every other part needs: the spreadsheet parser and the composer that lab scripts use (init_sheet.py); a .env writer that updates one key in place and never wipes a saved secret with a blank field (configuring.py); proxy resolution that takes the engineer's override first, then the environment, then the Windows system proxy, and never sends traffic for on-premises addresses through a proxy (proxy.py); a bridge to the operating system's trusted certificates (tls.py); and the GreenLake prerequisites with the firewall rules per region (prereqs.py).

21. The frontend, in brief

Where this fits: the browser box in section 2.

The screens are React with Grommet and HPE's theme, in frontend/src/. App.tsx is the shell: it reads the step registry from /app/profile, puts the three Prepare screens (Prerequisites, Initialisation sheet, Mode) in front, and renders the rail on the left and the current step on the right. steps/ has one file per step. ui/ has the shared pieces: StepShell (the page frame with the footer buttons and the confirmation tick), StatusLine, Section, the Console pane, and useStepState, which works out a step's state from the run's events.

useRunEvents.ts opens the event stream with the browser's EventSource and keeps the run's event list up to date. Each step component reads the events it cares about from that list. There is no other state store, so what you see is always what the backend recorded.

Two rules for screen work. Edit frontend/src only; frontend/dist is built from it after merge, and you never commit it. And follow docs/UX-GUIDELINES.md: one heading per page, plain language, a confirmation tick before anything that writes to an array, and screenshots at 1366 x 768 in the pull request.

22. Where data lives

The local database

SQLite, in adapters/persistence/sqlite.py. One file per Windows user, under %LOCALAPPDATA%\AlletraOnboard\, so a new version of the app keeps every earlier run.

TableHolds

run_eventsevery event, in order

The application never imports SQLite directly. It uses the RunStore interface from domain/ports.py, and tests hand it a temporary database.

Looking inside a run

On your laptop the database is .alletra_onboard/state.db in the app folder, and screenshots and documents go to .alletra_onboard/artifacts/. On a packaged install (the zip or the .exe) both are under %LOCALAPPDATA%\AlletraOnboard\; STATE_DATABASE_PATH and ARTIFACT_DIR override them. Records are JSON in a payload column, so sqlite3 and its json_extract are enough:

# the runs, newest first
sqlite3 .alletra_onboard/state.db "select run_id, serial_number, status, current_phase, updated_at
  from runs order by updated_at desc limit 5;"

# the last ten events of one run
sqlite3 .alletra_onboard/state.db "select created_at, phase, event_type, json_extract(payload,'$.message')
  from run_events where run_id='a9d2…' order by created_at desc limit 10;"

# what a run sent to devices, and whether each command was a write
sqlite3 .alletra_onboard/state.db "select json_extract(payload,'$.at'), json_extract(payload,'$.target'),
  json_extract(payload,'$.command'), json_extract(payload,'$.write')
  from run_commands where run_id='a9d2…' order by seq;"

A run stuck in running with no newer event is the thing to look for after a crash; it should not happen, and it is worth an issue with the last few events pasted in. Deleting the database file is the reset: the app recreates it empty on the next start.

Settings and secrets

  • config.py loads settings from the environment and the app folder's .env: the GreenLake client id and secret, the token URL, a proxy override. The coordinator re-reads them at every step, so credentials typed into the Prerequisites screen work without a restart.
  • One array credential per run (ADR 0013). coordinator.array_credential() takes it from the sheet: the Provisioning tab's array admin if there is one, else the DSCC system credential. Every step uses that one. The screen only learns whether a credential is present and where it came from.
  • One array address per run. The Initialisation tab's management address, or else the Provisioning tab's array host. The parser refuses a sheet where the two disagree. Before this rule, verify and the as-built once reached two different arrays in the same run.
  • Passwords are SecretStr values. domain/policies.redact() and the command log blank them out of anything stored or shown.

24. Tests

703 tests run in about ten seconds with no lab, no network and no array. Two things make that possible.

Factories. Every function that touches a device takes the client as an argument with a real default: array_cli_factory=make_array_cli, wsapi_factory=make_wsapi, vcenter_factory=make_vcenter; the step services take provision_factory, cloudinit_factory, dscc_factory, verify_fn. A test passes a fake. The small "dev servers" developers use to see screens with realistic data use the same trick: they swap in fakes that answer from saved captures, then start the normal app.

Real output as fixtures. The parsers are checked against real command output saved under tests/fixtures/ (rack13_fabric, rack13_wsapi, rc_pair, and others), captured on the lab and scrubbed of passwords and customer data. Device output never matches the documentation exactly; the captures are how the tests know the truth. When you need a new parser, capture the output on the lab first, save it, and write the parser against the file.

The rule that follows A test never calls GreenLake, an array, vCenter or a switch. If something needs the network, it is a lab script in lab/, run from the jump box, with its result attached to the pull request.

Running less than everything, from the app folder:

.venv/bin/python -m pytest -q                                   # all 703, about ten seconds
.venv/bin/python -m pytest -q tests/unit/test_workflow.py        # one file
.venv/bin/python -m pytest -q -k "zoning and not plan"           # by name
.venv/bin/python -m pytest -q -x --lf                            # stop at the first failure; only what failed last time
.venv/bin/python -m ruff check . --fix                           # lint, fixing what it can
cd frontend && npm run typecheck                                # TypeScript only

The test files are named after what they cover: test_workflow.py for the registry, test_storage_services.py for the step services with fake factories, test_api.py for routes through FastAPI's test client, test_init_sheet.py for the spreadsheet round trip, and one test_replication_*.py per replication module. When you add a module, add its test file next to these.

25. How to make common changes

Where this fits: the recipes behind sections 14 to 24. Each is a checklist of files, in the order you will touch them.

Add a step

  1. domain/models.py: add a WorkflowPhase value for it.
  2. domain/workflow.py: add a StepDef(key, label, phase, kind) to STEP_REGISTRY at the position it runs, and add the key to each preset in _MODE_STEPS that should include it. The label is what the engineer sees in the rail. Extend tests/unit/test_workflow.py.
  3. The work itself: a plain function in its own module under application/<context>/, taking the models it needs and the device clients as factory arguments with real defaults, returning a Pydantic result model. No coordinator, no HTTP in here.
  4. The step service: start_x() and async _run_x() in application/<context>/steps.py, in the shape shown in section 16. Preconditions raise StepPreconditionError with a sentence for the engineer. Event names: x.completed and x.failed, or the step.* ones.
  5. application/service.py: one delegating method.
  6. api/app.py: POST /runs/{run_id}/x next to its group, returning RunResponse; a body model in api/schemas.py if it takes input. The error mapping is already there.
  7. The screen: frontend/src/steps/XStep.tsx, reading its events through useStepState; import it in App.tsx and add the current.key === 'x' line beside the others. The rail picks the step up from /app/profile on its own. Add the call to frontend/src/api.ts.
  8. Tests: the service with fake factories (pattern in tests/unit/test_storage_services.py) and the route (pattern in tests/unit/test_api.py).
  9. Docs: the step tables in sections 15 and 17 of this page, docs/SCOPE.md, and a spec in docs/specs/ if the behaviour is new. If it reaches hardware, a lab script in lab/ and the needs live run label until it has run.

Add a field to the spreadsheet

  1. application/platform/init_sheet.py: add a (key, label, required, example) tuple to SECTIONS (Initialisation tab), PROVISIONING_SECTIONS or REPLICATION_SECTIONS. For the table tabs, add a column to the *_COLUMNS list. The label is the text the parser matches on, so never rename an existing one; engineers have filled sheets with it.
  2. Add the attribute to the model it belongs to: NetworkConfig, DsccSetupConfig or ArrayWorkItem in domain/models.py; ProvisioningIntent, VolumeRequest, DeclaredHost or HostSetRequest in domain/provisioning.py; the replication models in domain/replication.py. Then map it in parse_workbook_bytes().
  3. If it is required only for some modes, teach required_keys_for(); otherwise the required flag in the tuple is enough. build_template_bytes() reads the same table, so the blank template and the upload parser cannot drift apart.
  4. tests/unit/test_init_sheet.py: a round trip (compose a sheet, parse it, assert the value) and a case for the field missing.
  5. The app folder's README.md describes the sheet for engineers; add the field there.

Add a parser for a device command

  1. Capture the real output on the lab first: run the command from the Console tab or a lab script and save the text. Remove passwords, customer names and anything that is not the command's output.
  2. Save it under tests/fixtures/<set>/ (an existing set such as rc_pair or rack13_array, or a new folder with a short README.md saying which system and date). That folder already has an exception in the root .gitignore.
  3. Write the test first, pinned to the file: _FIXTURES = Path(__file__).resolve().parents[1] / "fixtures" / "<set>", then assert the specific values you can read in the capture.
  4. Write parse_x(text) -> Model as a pure function next to the models it fills, with no I/O. Column positions move between array versions; parse by header names where you can.
  5. Only then wire the command in. If it goes over SSH it must be on the allowlist; see the next recipe.

Allow a new SSH command

  1. It must be a read. If it is not, stop: writes go through the REST API, or wait for the separate write client in decision record 0015.
  2. Array: add the base command to ALLOWED_COMMANDS in adapters/array/cli_client.py. Options are allowed on the command line; shell characters never are. Switches: ALLOWED_READ in adapters/fabric/brocade_client.py.
  3. A test that the command is allowed and that a write verb is still refused (there is one of each in tests/unit/test_asbuilt_provisioned.py to copy).
  4. Say so in the pull request, on the checklist line about device commands. The owner has to agree to every allowlist change.

Add a route that only reads

  1. api/app.py: a GET next to its group with a response_model. If it reads a device, run the read with asyncio.to_thread inside with service.coordinator.recording(run_id):, so the commands show in the Console like a step's do. GET /runs/{id}/storage/objects is the pattern.
  2. The response model in api/schemas.py, or the domain model itself if it already fits.
  3. tests/unit/test_api.py with the test client and a fake service method.
  4. The call in frontend/src/api.ts, and the table in section 23 of this page.

Add a setting

  1. config.py: a field on Settings with a safe default. Its upper-case name is the environment variable and the .env key.
  2. Read it through coord.current_settings() inside steps, not from a value captured at start-up, so a change made on the Prerequisites screen applies without a restart.
  3. If engineers should set it on screen: the writer in application/platform/configuring.py, the /config route and its schema, and the Prerequisites screen.
  4. Document it in the table above and in the app folder's README.md. Never give a secret a default.

Change a screen

  1. Edit under frontend/src/ only. A step's file is in steps/; the shared frame, status line and console are in ui/. State comes from the run's events through useStepState; do not add a second store.
  2. Run onboard api and npm run dev side by side for instant reload. Write the words to docs/UX-GUIDELINES.md: one heading per page, plain sentences, a confirmation tick before anything that writes.
  3. npm run typecheck, then check.py. Screenshots at 1366 x 768 in the pull request. Never commit frontend/dist; the hook and the check refuse it, and the owner rebuilds it after merge.

Change what a step produces

  1. Change the result model (the Pydantic class the work function returns). Old runs in the database carry the old shape; the step service already treats an artifact it cannot read as absent, so give new fields defaults rather than making them required.
  2. Change the event's data if the screen needs the new field, and the message if the meaning changed. Then the component in frontend/src/steps/ that reads it, and the TypeScript type in api.ts.
  3. If the as-built shows it, application/documents/asbuilt.py reads the same events.
  4. Update the fixture-pinned tests, and the step tables in section 17 of this page.

27. Facts that are easy to get wrong

  • GreenLake device assignment is two PATCH calls: application and region first, subscription second.
  • In the GreenLake service catalog the id you need is serviceManager.id (nested), not application_id. You filter on status, but the field in the response is provisionStatus.
  • GreenLake writes return 202 and a Location header. Always poll until the job says SUCCEEDED, FAILED or TIMEDOUT.
  • DSCC region codes are not GreenLake region ids: ap-northeast is jp1, us-west is us1, eu-central is eu1, eu-west is uk1.
  • The array's setup page must be at https://169.254.…. A fail-prov-* error there is a GreenLake problem (the device or subscription is in the wrong state), not a network problem. Fix GreenLake; do not retry the wizard.
  • The array's own host list (showhost -d) is the truth about hosts. The switch's name server is filtered by zoning and can show another array's port as if it were a server.
  • A host set export appears in showvlun as a template row (hostname: set:<name>, active: false) plus one active row per member host and path. De-duplicate port addresses: the REST API repeats one once per array port it is logged in on.
  • Writing a zone into the switch's defined configuration does not activate it. Only the zoning check, which looks at real logins on both fabrics, opens the export gate.
  • A Remote Copy target carries one mode. The lab pair already has six synchronous groups, so a periodic group needs them paused, or a second target.
  • paramiko is pinned below version 4. Version 4 dropped the old key exchange that the lab's FOS 7 switches still require.
  • Shipped .ps1 files must be pure ASCII.

28. Glossary

Alletra Storage MP B10000
The HPE storage array this tool deploys. Block storage, Fibre Channel and iSCSI, managed through HPE GreenLake.
GreenLake, DSCC
HPE's cloud platform, and the Data Services Cloud Console inside it that manages storage arrays.
Jump box
A Windows machine in the customer's (or the lab's) network, next to the array. The tool runs there. The lab one is called labrat.
Initialisation sheet
The one spreadsheet the engineer fills in. Six tabs. One sheet, one array.
Run
One array, one set of steps, one event history.
Mode
Which steps a run has: a preset from the step registry, or Custom.
Step, step service
One screen and one job; and the class in application/*/steps.py that does it, with one start_* method per step.
Event
One record of what a step did, stored and streamed. The screen's only source of truth.
Artifact
A larger result saved with the run: the discovery report, the as-built file, replication results.
Plan
What apply will do, object by object: create, exists, update, conflict. Kept in memory until applied or dropped.
Removal set
The commands that would undo exactly what an apply created. Shown and documented, never run.
Export gate
The hosts the zoning check saw on both fabrics. Only they get volumes exported to them.
Allowlist
The commands an SSH client is willing to send. Anything else is refused before it leaves the process.
Console
Every command a run sent to a device, with its output, plus a read-only prompt.
Fixture
Real device output, scrubbed, saved under tests/fixtures/, that a parser is tested against.
WSAPI
The array's REST API. The only way the tool writes to an array.
WWPN, HBA
A Fibre Channel port's world-wide name, and the adapter card in a server that has such ports.
Fabric
One SAN switch network. Customers have two for redundancy; a host should be logged in on both.
Zone
A rule on a switch that lets one host port talk to one array port. The tool writes the commands; the SAN team applies them.
VV, VV set, host set, VLUN
A volume, a named group of volumes, a named group of hosts, and an export of a volume (or set) to a host (or set) with a LUN number.
CPG
A storage pool on the array that volumes are created in.
Remote Copy, RCIP, target, link, group
The array's replication feature; its IP ports; the partnership with another array; the connections of that partnership; a replicated set of volumes.
SSE
Server-Sent Events: one long HTTP response the browser listens to for live updates.
ADR, SPEC, BL-NN
A decision record in docs/adr/; a feature's requirements in docs/specs/; a work item's number, used in issue titles and branch names.
