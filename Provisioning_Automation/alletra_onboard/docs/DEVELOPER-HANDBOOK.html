1. The problem we solve

When a customer buys an HPE Alletra Storage MP B10000 array, an HPE field engineer goes to the customer's data centre to make it work. That takes a day or two and has many small steps, each on a different system: register the array in HPE GreenLake, connect it to the cloud through a setup page on the array itself, finish the setup in the Data Services Cloud Console (DSCC), find out which servers are cabled to which switch, plan array ports and SAN zoning for the SAN team, create the volumes and present them to the servers, set up snapshots or replication to a second array if the customer bought them, check that everything matches what was ordered, and write the hand-over document.

Each of those steps is well understood, and each is easy to get slightly wrong by hand. A typo in a port address, a volume exported to the wrong host, a zoning command pasted into the wrong fabric. The engineer also has to write the as-built document afterwards, by hand, from memory and screenshots.

This tool does that day for the engineer. It is a small web application that runs on the Windows "jump box", the laptop or server that sits next to the array in the customer's network. The engineer fills in one spreadsheet, uploads it, chooses what they want to do, and walks through the steps one at a time. The tool reads the real environment, shows the engineer exactly what it is about to change, waits for a yes, does it, checks the result, and writes the document.

Who uses it: HPE deployment engineers, on site, one array at a time. They are storage experts, not developers. The screens talk to them in plain words, and every screen says what the tool found, what it means, and what to do next.

2. The tool in one picture

Technically the tool is one Python program (built with FastAPI) listening on 127.0.0.1:8765. It serves a web page, built with React and HPE's design system, and an API that the page calls. The same program talks to the outside world on the engineer's behalf. Nothing else is involved: no server in the cloud, no database service, no login. The engineer is the only user, and the program runs only on their machine.

Three words you will meet in every file:

Run
One array, one chosen set of steps, and the full history of what happened. Everything the tool does is inside a run.
Step
One screen and one job: Discovery, SAN Zoning, Provision storage, and so on. The engineer presses a button; the step does its work and reports back.
Event
One line in a run's history: "discovery finished, here is the report". The screen is drawn from events, so a refresh or a restart loses nothing.

  4. application/provisioning/steps.py. The step services (DiscoveryZoningSteps, ArrayPortsSteps, ProvisioningSteps). Read start_discover and _run_discover first; every other step has that shape. How we work

8. From an issue to a merged change

Every change follows the same path. Nothing goes straight to main; github.hpe.com refuses it. The path has three lanes: you, GitHub, and the owner.

  1. Pick an issue. Labels show the area (area/replication, area/docs, …) and the state (build, needs live run, blocked, in progress). Assign it to yourself. For anything large, write a few lines in the issue about how you plan to do it before you start, so the owner can steer early. If there is no issue for what you want to do, open one; its title starts with the next free BL-NN number (the list is in docs/TRACKER.md).
  2. Branch from an up-to-date main: git switch main && git pull && git switch -c feat/bl-NN-short-name. One issue per branch.
  3. Make the change. Code and tests together. Update any document that describes the behaviour you changed, including this page: if a section here is now wrong, fix it in the same pull request. Commit as often as you like; the merge squashes it to one commit.
  4. Run scripts/check.py until it ends with PASS (section 9).
  5. Push and open the pull request on github.hpe.com (section 10).
  6. github.hpe.com checks the rules: the change must come through a pull request, and the owner must approve it. A push after approval needs approval again.
  7. Review. The owner reads it and comments. Answer each comment, push, and ask for another look.
  8. Squash and merge. The owner merges. Your commits become one commit on main with the pull request's title as its message, your branch is deleted, and Closes #N in the description closes the issue.
  9. After the merge the owner runs one script that rebuilds the screens and refreshes everything downstream (section 13).

If your change reaches an array, a switch, vCenter or GreenLake, it also needs a run on the lab (section 12). Until then the issue keeps the needs live run label.

13. After a merge, and releases

You do not need to do any of this, but you will see it happen.

After merging, the owner runs scripts/after_merge.sh. It pulls main, rebuilds the screens from frontend/src and commits them if they changed, refreshes jumpbox-package, and refreshes the rolling "latest" download zip on github.hpe.com. That is how your change reaches the engineers.

Numbered releases (vX.Y.Z) are also made by hand. The owner tags main, and on a Windows laptop on the VPN runs scripts/publish_release.ps1 -Tag vX.Y.Z -BuildExe. It builds three Windows .exe bundles (one that uses the installed browser, one with a browser inside, one with only the onboarding steps), runs a self-test and a smoke test on each, and attaches them to the release. The script refuses if the tag is not on github.hpe.com or the checkout is not the tagged code.

15. A run

Where this fits: the spreadsheet and the arrow into the tool, in section 1.

A run starts with the spreadsheet and ends with the hand-over document. Here is how it comes into being.

  1. The engineer uploads the spreadsheet. platform/init_sheet.py reads the workbook layout, core tabs and array-port tabs, while platform/init_sheet_tabs.py parses the optional workflow tabs (Replication, Snapshots, Migration). The workbook mirrors HPE's initialisation worksheet: core tabs (Initialisation, Provisioning, Volumes, Hosts, Host sets) plus optional tabs (Replication, Replication network, iSCSI network, Peer ports, Migration, Snapshots). Parsing produces ArrayWorkItem (array identity, network, GreenLake and DSCC settings) and ProvisioningIntent (targets, hosts, volumes, sets and any optional tabs). A workbook that names two different arrays is refused. Only a problem in the initialisation fields refuses the upload; problems in optional tabs are listed and stop only a run whose chosen steps use that tab.
  2. The parsed sheet waits on the server. It is stored under a one-time token in pending_sheets (with passwords encrypted at rest), and the browser gets only the token and a summary with passwords blanked. Device passwords never go back to the browser.
  3. The engineer picks a mode, and POST /runs/from-sheet validates the chosen steps against the held workbook and turns the token into a run. The token is used up. From here on, every step reads what it needs from the run.

16. What happens when you press a button

Where this fits: inside any one step box in section 1.

Every step works the same way, so this one sequence explains most of the application layer. Take "Create storage objects" on the Provision storage screen as the example.

  1. The route calls one method on the service. application/service.py is a thin front door. It holds RunCoordinator, ConsoleService and the step services (OnboardingSteps, DiscoveryZoningSteps, ArrayPortsSteps, ProvisioningSteps, ReplicationSteps, SnapshotSteps, DocumentSteps) and passes each call to the right one.
  2. The step service checks its preconditions. If they fail it raises StepPreconditionError with a sentence an engineer can read, and the route returns HTTP 409. For an array write, it also checks plan_id with check_approval, requests a single-use Approval from coord.issue_approval, and pops the held plan so it cannot be applied twice.
  3. The coordinator starts the work in the background (spawn). Only one task (or unspent approval) may be live per run at a time. A second button press gets RunBusyError, also a 409.
  4. Blocking device work runs in a thread. Read steps use asyncio.to_thread; write steps use coord.run_approved(approval, fn), which binds the durable undo saver onto the approval and spends the approval in the worker thread's own finally block.
  5. Results and progress are typed events. The step calls coordinator.emit(run_id, phase, event_type, message, data) using an EventType[D] constant from domain/events.py, so pyright checks the payload model at every emit site. The run's status is set separately with set_state.
  6. A crash cannot leave a run stuck. The task runs inside _guarded. An unexpected exception becomes a step.crashed event and a retryable failure; an unclosed write leaves its apply_in_progress record on disk for automatic recovery on reopen (section 18).
  7. Every device command and trust check is bound to the task. spawn copies contextvars with command_log.bind and device_trust.bind. Each adapter records its commands with secrets redacted, feeding the Console tab under each step.

def start_storage_apply(self, run_id, *, approved_plan):
    run, _intent, _discovery = self._ready(run_id)
    inputs = self._previewed_plan(run_id)                                   # 2. preconditions
    if inputs is None:
        raise StepPreconditionError("no provisioning plan to apply — run the provisioning preview first")
    if inputs.plan.blockers:
        raise StepPreconditionError("the plan has conflicts that must be resolved on the array first: ...")
    check_approval(approved_plan, inputs.plan.plan_id)                      # the id of the plan that was ticked
    approval = self._coord.issue_approval(run_id, "storage", {"A": inputs.intent.array})
    self._plan.pop(run_id, None)
    self._coord.spawn(run_id, self._run_storage_apply(run, inputs, approval), approval=approval)  # 3. background
    return run

async def _run_storage_apply(self, run, inputs, approval):
    coord = self._coord
    coord.set_state(run, RunStatus.RUNNING, WorkflowPhase.STORAGE_PROVISION)

17. How the screen knows what happened

Where this fits: the "live events" arrow from the backend to the browser in section 2.

Events are the record, not a side channel. Each one has the run id, the phase, a type such as storage.applied, a message written for the engineer, a data payload (the report, the plan, the result) and a time. When a step emits one, two things happen: it is appended to the run_events table in SQLite, and it is pushed to every open browser tab over Server-Sent Events on GET /runs/{id}/stream (handled by api/routes/events.py with a periodic heartbeat set by SSE_HEARTBEAT_S in api/routes/common.py).

The screen is drawn from the events alone. The newest storage.previewed event is the plan on screen; a storage.applied newer than that preview is the result; a step.crashed or *.failed marks the step as failed. When you refresh the page, or restart the backend, frontend/src/useRunEvents.ts replays GET /runs/{id}/events, opens SSE, deduplicates by event_id, and the screen is exactly as it was.

Block provisioning, Remote Copy partnerships, Remote Copy groups and snapshots all follow the same four stages under least privilege (ADR 0031):

  1. Plan (readers only). build_plan() reads live state through read-only clients (WsapiReader, ArrayCliClient) and marks every object create, exists, update or conflict. Conflicts become blockers. The plan and its frozen inputs are held in memory under a fresh plan_id and emitted as a *.previewed event.
  2. Approve and issue Approval. The screen shows the plan and a confirmation tick box. Apply checks check_approval(approved_plan, plan_id), pops the held plan, and asks RunCoordinator.issue_approval for a single-use, in-memory Approval (domain/approval.py) that is never copied or saved to disk and is tied to that run, purpose and array side(s). While an approval is unspent, the run stays busy.
  3. Apply with least privilege and pre-write undo. Inside coord.run_approved(approval, fn), writer factories (make_wsapi_writer in application/runs/writer_clients.py, make_rc_writer in application/replication/clients.py, make_snap_writer in application/snapshots/clients.py) pull credentials only from Approval.creds_for, and every write calls approval.require_live(). Before each write, recorded_write (application/runs/apply_record.py) saves an inspect-first note and the removals recorded so far (including pre-recorded removal lines for scoped SSH commands) into SQLite's apply_in_progress artifact, then drops the note and saves that write's confirmed removal line after read-back. When the worker thread finishes, run_approved marks approval.spent = True in its own finally block.
  4. Removal set and crash recovery. Emitting any terminal apply event closes apply_in_progress. If the process crashes mid-apply, reopening the run (get_run) or starting the app (recover_interrupted_applies) promotes the unclosed record into a failed apply event with its removal set and inspect-first notes intact. Removal commands are shown with a copy button and written into the as-built document; the tool never runs them.

WSAPI v1 is split into two classes: WsapiReader in adapters/array/wsapi_client.py (reads only, wrapping python-3parclient pinned in pyproject.toml, with connect() acting as the HTTP 503 readiness gate) and WsapiWriter in adapters/array/wsapi_writer.py (mutating calls, each gated by approval.require_live()). The S2-* import-linter rules in pyproject.toml forbid any read-only module from importing a writer or writer factory (with no exceptions), and ruff SLF001 stops application code from bypassing a reader through private attributes.

24. Tests

The backend unit and contract test suite and the frontend vitest unit tests run in seconds with no lab, no network and no array. Three mechanisms make that possible:

Test guards (tests/conftest.py). Autouse fixtures enforce STANDARD X1 and T4 across pytest: _no_network blocks non-loopback sockets and DNS lookups, _run_in_a_scratch_folder isolates working directories, _isolate_settings_from_dotenv blocks local .env leakage, and _validate_emitted_events validates every emitted event against domain/events.py.

Injectable factories. Every function that touches a device takes its client factory as an argument with a real default (readers such as make_array_cli, make_wsapi, make_vcenter, and approval-gated writers such as make_wsapi_writer, make_rc_writer, make_snap_writer). Step services accept provision_factory, cloudinit_factory, dscc_factory and verify_fn. Tests pass fakes — including fake devices that fail mid-apply to verify pre-write undo persistence.

Real output as fixtures. Parsers are pinned to scrubbed command output under tests/fixtures/ (rack13_fabric, rack13_wsapi, rc_pair, and others), captured on the lab with passwords and real emails scrubbed (use lab-user@example.com). When you need a new parser, capture real output on the lab first, save it under tests/fixtures/, and pin the test to that file.

The rule that follows A test never calls GreenLake, an array, vCenter or a switch. If something needs the network, it is a lab script in lab/, run from the jump box, with its validation record attached to the pull request.

Running targeted checks from the app folder:

.venv/bin/python -m pytest -q                                   # full Python test suite
.venv/bin/python -m pytest -q tests/unit/test_workflow.py       # one file
.venv/bin/python -m pytest -q -k "zoning and not plan"          # by name
.venv/bin/python -m pytest -q -x --lf                           # stop at first failure; only last failed
.venv/bin/python scripts/check.py --quick                       # all static, type, lint and frontend checks
cd frontend && npm run typecheck && npm run lint && npm test    # frontend checks alone

Test files mirror what they cover: test_workflow.py for the registry, test_storage_services.py for step services with fake factories, test_api.py for routes through FastAPI's test client, test_init_sheet.py for workbook round trips, test_cli_allowlist.py for SSH guards, test_trust_checks_off.py for unchecked links, and per-area files for replication and snapshots.

25. How to make common changes

Where this fits: the recipes behind sections 14 to 24. Each is a checklist of files, in the order you will touch them.

Add a step

  1. domain/models.py: add a WorkflowPhase value for it.
  2. domain/workflow.py: add a StepDef(key, label, phase, kind, lab_script, no_lab_script) to STEP_REGISTRY at the position it runs (naming its lab script or why there is none, STANDARD X4), and add the key to each preset in _MODE_STEPS that should include it. Extend tests/unit/test_workflow.py.
  3. The work itself: plain functions under application/<context>/ taking models and injectable client factories (readers for read/plan; Approval-gated writers only inside an apply module). Raise/catch DeviceError subclasses from domain/errors.py; no coordinator or HTTP in here.
  4. domain/events.py: register every new event type (_event / _plain) with its Pydantic payload model.
  5. The step service: start_x() and async _run_x() in application/<context>/steps.py, in the shape shown in section 16 (using typed events.* constants and, for writes, issue_approval + run_approved).
  6. application/service.py: one delegating method.
  7. api/routes/ (and api/schemas.py): add the route to the matching area router (or register a new router in api/app.py). Then run .venv/bin/python scripts/api_types.py to update frontend/generated/api.ts.
  8. The screen: frontend/src/steps/<Name>Step.tsx reading events through useStepState; wire it in frontend/src/App.tsx and add the API call and generated type alias in frontend/src/api.ts. The rail picks the step up from /app/profile on its own.
  9. Tests and docs: service tests with fake factories, route tests, scripts/check.py, docs/SCOPE.md, a spec in docs/specs/ if new behaviour, and a lab script in lab/ if it touches hardware.

Add a field to the spreadsheet

  1. application/platform/init_sheet.py: add the tuple to SECTIONS, PROVISIONING_SECTIONS or the matching *_COLUMNS list. Never rename an existing label; engineers have filled workbooks with it.
  2. Add the field to its domain model (domain/models.py, domain/provisioning.py, domain/replication.py, domain/snapshots.py, domain/network.py, domain/peer_ports.py or domain/migration.py) and map it in init_sheet.py (or application/platform/init_sheet_tabs.py for Replication, Snapshots and Migration).
  3. If required only for certain modes, teach required_keys_for(); build_template_bytes() reads the same definitions so the blank template and upload parser stay in sync.
  4. tests/unit/test_init_sheet.py: add a round-trip test and a missing-field case. If the upload summary schema changed, run scripts/api_types.py (without changing response_model= on /init-sheet/upload).
  5. Document the field in the app folder's README.md.

Add a parser for a device command

  1. Capture real output on the lab first and scrub passwords, customer names and real email addresses (use lab-user@example.com).
  2. Save it under tests/fixtures/<set>/ with a short README.md naming the system and date.
  3. Write the test first, pinned to that fixture file, asserting concrete values from the capture.
  4.   5. Only then wire the command in (checking the SSH allowlist if over SSH).

Allow a new SSH command

  1. It must be a read. If it changes an array, stop: writes use WsapiWriter, or require a dedicated write-scoped SSH client argued in its own ADR under ADR 0025 (today only ArrayRcCliClient and ArraySnapCliClient). Switch writes are never allowed (ADR 0012).
  2. Array reads: add the base command to ALLOWED_COMMANDS in adapters/array/cli_client.py (keeping acting options in _ACTION_OPTIONS blocked). Switch reads: ALLOWED_READ in adapters/fabric/brocade_client.py.
  3. Add tests in tests/unit/test_cli_allowlist.py (and tests/unit/test_asbuilt_provisioned.py where relevant) proving the read is allowed and write verbs / metacharacters remain refused.
  4. State the allowlist addition plainly in the pull request checklist; the owner must agree to every allowlist change.

Add a route that only reads

  1. Add the GET route in the matching router under api/routes/ (not directly in api/app.py) with a response model in api/schemas.py (or a domain model). If it reads a device, run the read with asyncio.to_thread inside with service.coordinator.recording(run_id): so commands show in the Console.
  2. Run .venv/bin/python scripts/api_types.py to regenerate frontend/generated/api.ts.
  3. Add a test in tests/unit/test_api.py, wire the call in frontend/src/api.ts, and update section 23 of this page if you added a new route group.

Add a setting

  1. config.py: add a field on Settings with a safe default (never give a secret a default). Its upper-case name is the environment variable and .env key.
  2. Read it through coord.current_settings() inside steps so Prerequisites edits take effect without a restart.
  3. If engineers edit it on screen: update application/platform/configuring.py, api/routes/prereqs.py, api/schemas.py, run scripts/api_types.py, and update the Prerequisites screen.
  4. Document it in section 22 of this page and in the app folder's README.md.

Change a screen

  1. Edit under frontend/src/ only. Put step screens in steps/ (never importing another step) and shared blocks in ui/. Keep fetch in api.ts and EventSource in useRunEvents.ts.

  2. Run .venv/bin/python scripts/api_types.py to regenerate frontend/generated/api.ts, then update frontend/src/api.ts (if adding a new type alias) and the step component in frontend/src/steps/.

27. Facts that are easy to get wrong

  • GreenLake device assignment is two PATCH calls: application and region first, subscription second.
  • In the GreenLake service catalog the id you need is serviceManager.id (nested), not application_id. The response field is provisionStatus (not status), and the live API rejects provisionStatus eq ... and combined and filters with HTTP 400, so adapters/greenlake/service_catalog.py reads unfiltered and filters in Python.
  • GreenLake writes return 202 and a Location header. Always poll until the job says SUCCEEDED, FAILED or TIMEDOUT.
  • Rate limits use one token bucket per endpoint family (domain/policies.py); always sleep outside the lock.
  • DSCC region codes are not GreenLake region ids: ap-northeast is jp1, us-west is us1, eu-central is eu1, eu-west is uk1.
  • The array's setup wizard address must be link-local: IPv4 https://169.254.x.x or bracketed IPv6 https://[fe80::…] (validated once in domain/cloudinit_url.py; 169.254.0.0 is the workbook's placeholder). A fail-prov-* error there is a GreenLake state problem (device or subscription), not a network problem — fix GreenLake, do not retry the wizard.
  • Never add or change response_model= on the three initialisation routes (/app/profile, /init-sheet/upload, /runs/from-sheet); attach OpenAPI documentation models via responses={200: {"model": ...}} only so their wire bytes stay identical (ADR 0032).
  • The array's own host list (showhost -d) is the truth about hosts. The switch's name server is filtered by zoning and can show another array's port as if it were a server.
  • A host set export appears in showvlun as a template row (hostname: set:<name>, active: false) plus one active row per member host and path. De-duplicate port addresses: WSAPI repeats one once per array port it is logged in on.
  • Writing a zone into the switch's defined configuration does not activate it. Only the zoning check, which looks at real logins on both fabrics, opens the per-host export gate.
  • A Remote Copy target carries one mode. Setting syncPeriod and policies on a group takes two separate WSAPI PUTs (encoded in WsapiWriter).
  • paramiko is pinned below major 4 in pyproject.toml because older Brocade FOS switches require legacy key exchange algorithms dropped in paramiko 4.
  • Shipped .ps1 files must be pure ASCII.

Alletra Storage MP B10000
The HPE storage array this tool deploys. Block storage (Fibre Channel and iSCSI) plus read-only Unified File discovery, managed through HPE GreenLake.
GreenLake, DSCC
HPE's cloud platform, and the Data Services Cloud Console inside it that manages storage arrays.
Jump box
A Windows machine in the customer's (or the lab's) network, next to the array. The tool runs there. The lab one is called labrat.
Initialisation sheet
The one workbook the engineer fills in: core tabs plus optional tabs for array ports, replication, snapshots and migration. One sheet, one array.
Run
One array, one set of steps, one event history, plus its artifacts, command log and device trust pins.
Mode
Which steps a run has: a preset from domain/workflow.py, or Custom.
Step, step service
One screen and one job; and the class in application/*/steps.py that runs it, with one start_* method per step.
Event
One typed record from domain/events.py of what a step did, stored in SQLite and streamed over SSE. The screen's only source of truth.
Artifact
A larger result saved with the run in run_artifacts: the discovery report, the export gate, the as-built file, or an apply_in_progress undo checkpoint.
Plan
What apply will do, object by object: create, exists, update, conflict. Held in memory under a plan_id until applied or dropped.
Approval
A single-use, in-memory token (domain/approval.py, never copied or saved to disk) issued by RunCoordinator after the operator approves a plan or authorises failover; required to open any array writer.
Removal set
The copy-paste array CLI commands that undo only what an apply created. Before each WSAPI write, an inspect-first note and the removals so far are saved (with that write's line saved on return); for scoped SSH, each removal line is written before the command. Shown and documented, never run by the tool.
Export gate
The hosts the zoning check confirmed on both fabrics (or logged in over iSCSI). Only they get volumes exported to them.
Allowlist
The commands a read-only SSH client (ArrayCliClient, BrocadeClient) or a write-scoped SSH client (ArrayRcCliClient, ArraySnapCliClient) is permitted to send. Everything else is refused before leaving the process.
Console
Every redacted command a run sent to a device or cloud API, with its output, plus a read-only prompt.
Fixture
Real device output, scrubbed, saved under tests/fixtures/, that a parser is tested against.
WSAPI
The array's REST API: /api/v1 for block reads (WsapiReader) and approved writes (WsapiWriter), and /api/v3 GET-only (WsapiV3Client) for Unified File reads.
Gate
scripts/check.py, the pre-pull-request suite enforcing docs/STANDARD.md.
WWPN, HBA
A Fibre Channel port's world-wide name, and the adapter card in a server that has such ports.
Fabric
One SAN switch network. Customers have two for redundancy; a host should be logged in on both.
Zone
A rule on a switch that lets one host port talk to one array port. The tool writes the commands; the SAN team applies them.
VV, VV set, host set, VLUN
A volume, a named group of volumes, a named group of hosts, and an export of a volume (or set) to a host (or set) with a LUN number.
CPG
A storage pool on the array that volumes are created in.
Remote Copy, RCIP, RCFC, target, link, group
The array's replication feature; its IP or Fibre Channel ports; the partnership with another array; the connections of that partnership; a replicated set of volumes.
SSE
Server-Sent Events: one long HTTP response the browser listens to for live updates.
ADR, SPEC, BL-NN
A decision record in docs/adr/; a feature's requirements in docs/specs/; a work item's number, used in issue titles and branch names.
