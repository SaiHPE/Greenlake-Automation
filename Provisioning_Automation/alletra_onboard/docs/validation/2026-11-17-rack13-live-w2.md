## Findings

1. **BL-21, blocker on OS 10.6.0: `showsched` with a schedule is not read.** OS 10.6.0 prints
   `Id SchedName … Alert Rebal NextRunTime`; rows start with the Id (`6 zz_snap_probe …`). The OS 10.5
   captures start with `SchedName` and have no `Rebal`. `showsched_readable` looks for a line starting
   `SchedName`, so it says False; `parse_showsched` returns `[]`. Effects on any OS 10.6 array: the
   apply creates the schedule and stops at the read-back (the removal line stays, with a note); as
   soon as any schedule exists, the snapshot preview and Check snapshots fail with *Could not read
   10.132.30.121: showsched did not list the schedules*, and the as-built's Snapshots section says the
   array could not be read. Evidence: `tests/fixtures/rack13_snap/showsched_one.txt`, pinned by
   a strict xfail test. Proposed fix (`application/snapshots/read.py`): take the header's columns by
   name, accept `Id` before `SchedName` (drop the first token of each row when it does), and allow an
   optional `Rebal` token before NextRunTime in `_SCHED_ROW`; `showsched_readable` to accept a header
   whose first or second token is `SchedName`.
2. A provisioning-and-snapshots workbook needs a host and a host set: an empty host set is a plan
   blocker and the Host sets tab must have a row. Not a bug; the lab used a never-logged-in iSCSI host
   with an `example.com` IQN.
3. **BL-25: the `gw … -vlan N` line is refused on a port whose link is up** (*Port 0:4:2 is not in
   offline state. To modify the Gateway IP, please use controlport to offline the port first.*). The
   `addr` line had already brought the port up, so the printed pair leaves an interface without its
   gateway. A port carrying sessions cannot be taken offline. ADR 0017 point 6 needs the owner: drop
   the gateway column, or find a form that sets the address and gateway together.
4. **BL-25: `offline` on an iSCSI port without an address does not mean no link.** 0:4:2 read
   `offline`, `0.0.0.0`, rate `n/a`, and came up `ready 10Gbps` the moment it had an address. The
   plan's note (*no host reaches it until the link is up*) is wrong for such a port, and the lab survey
   called these ports "no link".
5. BL-25: once the row is a conflict the plan's `switch_handoff` is empty, though R3 asks for a line
   per port with a planned **or existing** VLAN; the as-built still printed it.
6. BL-25 first slice: the page and API print the add lines but no undo line. `removal_lines` only
   reads apply outcomes, so a consultant who pastes the lines has no removal set. Proposed: print
   `delete_line(nsp, vlan)` per create in the plan, as the peer-port section prints its undo.
7. BL-25: on a port with only a VLAN address `showport -iscsi` shows that address in the base columns
   (no `*`), and `read_port_network` takes it as the port's untagged address. A second VLAN row on that
   port in the same network would then be refused as *the network of … the port's own untagged
   address*. Check `showport -iscsivlans` for an `untagged` row before calling a base address untagged.
8. **BL-26: `controlport offline <nsp>` always asks for confirmation and has no `-f`** (OS 10.6.0
   syntax `controlport offline <node:slot:port>...`). Over a non-interactive SSH exec it waits for an
   answer until the session times out; pasted as a block in the CLI, the next line would be taken as
   the answer to *select q=quit y=yes n=no*. The printed command set is not safe to paste as it stands,
   and ADR 0018's `offline` form breaks ADR 0025 condition 6 (no prompts). The removal set's
   `controlport rst <nsp>` has no `-f` either, although `rst` takes one. Owner to decide: print the
   lines one at a time with the answer the array will ask for, or find a way to the mode change
   without the prompt (and add `-f` to the `rst` line).
9. BL-26: the plan does not look at port pairs. `help controlport` (OS 10.6.0) says ports 1–2 and
   3–4 of a quad-port FC card share a mode on LSI adapters. E18U31's capture shows mixed modes in one
   pair, so the B10000 card may not enforce it, but nothing on rack13 proves it. A note naming the
   pair partner and what it serves would cost little.
10. Minor: with a Peer ports tab only, the ports preview says *Read 10.132.30.121*; with the iSCSI
    tab it says *Read rack13-ARCUS*.
