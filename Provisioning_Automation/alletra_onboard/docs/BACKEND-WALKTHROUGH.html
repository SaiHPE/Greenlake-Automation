1. The big picture

The app is a local web application. One Python process (FastAPI) listens on 127.0.0.1:8765. It serves the React user interface and a REST API. It runs on the field engineer's Windows jump box, next to the array, and that engineer is its only user. Nothing is shared, nothing is multi-tenant.

The engineer uploads one filled workbook (the initialisation sheet), picks what to do (the mode), and then walks through steps one at a time. Each step reads from, or writes to, one of six kinds of outside system:

It is a desktop tool that happens to use a browser as its screen. One engineer, one array, one process.

3. A run

Everything the tool does happens inside a run: one array, one mode, one record with its own event history. There is never a run that touches two arrays; the sheet parser refuses a workbook that names two.

From a workbook to a run

  1. The sheet is parsed (platform/init_sheet.py). The workbook mirrors HPE's official initialisation worksheet so it is familiar to the engineer. Its tabs are Initialisation, Provisioning, Volumes, Host sets, Hosts and Replication. Parsing produces two objects:
    ArrayWorkItem
    serial and part number, network settings, the GreenLake workspace details, the DSCC set-up values, contact details.
    ProvisioningIntent
    the array and target credentials (vCenter, both switches), the hosts, volumes and host sets to create, the exports, and the replication rows (peer array, volume sets, mode).
  2. The parsed sheet is held on the server behind a single-use token (pending_sheets table). The browser gets the token and a masked summary. Device passwords never travel back to the browser.
  3. The operator picks a mode, and POST /runs/from-sheet turns the token into a run (RunCoordinator.create_run). The token is consumed.

Modes and the step registry

The mode decides which steps the run has. The list of steps exists in one place, domain/workflow.py, and the user interface reads it from GET /app/profile. There is no second copy in the frontend. If you add a step, you add it there and nowhere else.

4. How a step runs

Every step follows the same pattern. If you understand this one sequence you understand nine tenths of the application layer.

  1. A route calls one start_* method on OnboardingService (application/service.py). The service is a thin front: it holds the RunCoordinator and the five step services (OnboardingSteps, DiscoveryZoningSteps, ProvisioningSteps, ReplicationSteps, DocumentSteps) plus the ConsoleService, and delegates one to one.
  2. The step service checks its preconditions and raises StepPreconditionError if they fail (the route turns that into HTTP 409 with a sentence the operator can read). Examples: zoning before discovery; apply without a previewed plan; a plan with blockers.
  3. RunCoordinator.spawn() starts the work as an asyncio task. There is one task per run at a time. A second request while one is running gets RunBusyError (HTTP 409). This is why the UI never has two buttons busy at once.
  4. Blocking device work runs in a thread (asyncio.to_thread). paramiko, HPE's 3PAR SDK and pyvmomi are all blocking libraries; the event loop stays free to serve the UI.
  5. Progress and results are events. The step calls coordinator.emit(run_id, phase, event_type, message, data). Long steps emit phase.progress lines on the way. From a thread they marshal back to the loop with call_soon_threadsafe.
  6. The run status is set separately with set_state(): RUNNING at the start, then READY, WAITING_FOR_OPERATOR (there is something to approve) or RETRYABLE_FAILURE.
  7. A crash cannot leave a run stuck. The task runs inside _guarded(): any unexpected exception becomes a step.crashed event and a retryable failure.
  8. Every device command is recorded. spawn() binds a recorder to the task's context, so every adapter call to command_log.record(...), including from threads, lands on this run, with secrets redacted. That is what the Console shows.
# application/provisioning/steps.py, shortened: the shape every step has
def start_storage_apply(self, run_id):
    run = coord.get_run(run_id)
    plan = self._previewed_plan(run_id)                 # 2. preconditions
    if plan is None:
        raise StepPreconditionError("no provisioning plan to apply — run the preview first")
    if plan.blockers:
        raise StepPreconditionError("the plan has conflicts that must be resolved on the array first: ...")
    coord.spawn(run_id, self._run_storage_apply(run, intent, discovery))   # 3. background
    return run

async def _run_storage_apply(self, run, intent, discovery):
    coord.set_state(run, RunStatus.RUNNING, WorkflowPhase.STORAGE_PROVISION)
    coord.emit(run.run_id, phase, "storage.apply.started", "Creating host, volumes and exports…")
    result = await asyncio.to_thread(storage_provision.apply_plan, intent, discovery, ...)   # 4. thread
    coord.set_state(run, RunStatus.RETRYABLE_FAILURE if result.error else RunStatus.READY, phase)
    coord.emit(run.run_id, phase, "storage.apply.failed" if result.error else "storage.applied",
               result.error or summary, data={"result": result.model_dump(mode="json")})   # 5. event

A button press is a request that returns at once. The work runs in the background, and the only way it talks to the screen is by emitting events.

5. Events and the screen

Events are the record of truth, not a side channel. Each RunEvent has a run id, a phase, an event_type, a message for the operator, a data payload and a timestamp. When emitted it is:

  • appended to SQLite (run_events), and
  • published on an in-memory bus (application/runs/event_bus.py) that fans out to every open GET /runs/{id}/stream connection as Server-Sent Events.

The browser derives each step's state from the events alone: the newest storage.previewed is the plan on screen; a storage.applied newer than that preview is the result; a step.crashed or *.failed marks the step failed. A page refresh, or a server restart, replays GET /runs/{id}/events and the screen is exactly as before.

Why this matters when you change something If you change what a step produces, you change the data of its event and then the component in frontend/src/steps/ that reads it. The message is operator text: plain words, what happened, what it means, what to do next. No ADR, SPEC or version numbers.

6. Plan, approve, apply

The tool changes an array in two places only: Provision storage and Replication (and the failover test, which drives Remote Copy). Both use the same safeguard, and any future write must too.

  1. Preview. build_plan() reads the array and marks every object create, exists (same name, same attributes), update (exists, apply will add to it) or conflict (same name, different attributes: apply cannot fix it). Conflicts become blockers. The plan is emitted as storage.previewed.
  2. Approve. The screen shows the plan and a tick box. The Create button does nothing without the tick.
  3. Apply re-checks the approval. The previewed plan is held in memory only, paired with the exact discovery it was built from. It is thrown away if discovery is re-run or the composition is edited, and it never survives a restart. An approval is a decision, not a result, so it must not outlive its inputs. A plan with blockers is refused. Replication adds one more gate: the link must have been checked first.
  4. Apply is idempotent. Every create is lookup-before-create or catches the array's "already exists" answer; a re-run reports exists instead of failing.
  5. Apply returns a removal set: the commands that would undo exactly what it created, in dependency order (exports, sets, volumes, host sets, hosts). The tool never runs them. They are shown to the operator and written into the as-built.

The WSAPI client

adapters/array/wsapi_client.py wraps HPE's python-3parclient (4.2.14 or newer; older versions post to the wrong credentials path on this platform). Design points baked in: login is the readiness gate (a degraded array answers 503 and we stop there); every create is idempotent; the array's address is bypassed from the proxy; the self-signed certificate is accepted; every call is recorded for the console with the password redacted.

Replication (Remote Copy) and the failover test

Remote Copy has three layers on the array: the transport (RCIP ports and addresses), the partnership (targets and links) and the groups. Today the tool reads all three and writes the third.

ModuleWhat it does
replication/read.pyReads one array's Remote Copy state over read-only SSH (showrcopy, showrctransport, showport -rcip, CPGs, volume sets) into a ReplicationArrayView. Every parser is pinned to the lab pair's captures in tests/fixtures/rc_pair/.
replication/plan.pyFrom the two views and the sheet's Replication tab: the blocking findings (no partnership, links down, a mode the target already carries, a missing peer CPG, a volume already in a group) and the plan (groups to create, volumes to admit, what already exists).
replication/link_check.pyRuns checkrclink between the pair (server on one side, client on the other) and reads the measured latency. Sync replication has a latency limit; above it the operator decides whether to continue. Apply is refused until this has run.
replication/apply.pyCreates the group, sets the mode and period, admits each volume (creating the secondary on the peer), starts the group. All WSAPI. Returns a removal set for each array.
replication/verify.pyReads both arrays again: links Up, each group Started with the right role on each side, volumes Synced. It never retries a write; it names the HPE procedure instead.
replication/failover.pyThe failover test: stop, fail over to the peer, recover, restore, through WSAPI disaster-recovery actions, polling the group's role and sync state and timing each leg. The record goes into the as-built.

Verify and the as-built document

DocumentSteps runs the two read-only steps at the end of every mode. Both run after the run's outcome is decided and never change the run status: a failed verification cannot un-succeed an onboarding.

  • Verify configuration (documents/verification.py): logs in over SSH and compares the array's running configuration (system name, management address, netmask, gateway, DNS, NTP, time zone, …) field by field with what the sheet asked for, then adds the array's status check (checkhealth) and inventory. A per-field report, never a gate.
  • As-built document (documents/asbuilt.py, asbuilt_parse.py, asbuilt_docx.py): reads the array (show*), parses the tables, and fills HPE's Word template with python-docx, keeping its boilerplate: configuration and inventory, what this run created and its removal set, the zoning command set, the replication groups, the link check and the failover test result. The .docx is saved as a run artifact and served by GET /runs/{id}/asbuilt/download.

Platform

application/platform/ is the plumbing every context needs: the sheet parser and composer (init_sheet.py), the in-place .env writer that never wipes a saved secret with a blank field (configuring.py), proxy resolution that follows the operator's override, then the environment, then the Windows system proxy, with on-premises addresses bypassed (proxy.py, ADR 0008), the TLS trust bridge to the OS store (tls.py), and the GreenLake prerequisites with the firewall rules per region (prereqs.py).

9. Data and settings

SQLite

adapters/persistence/sqlite.py, one file per Windows user under %LOCALAPPDATA%\AlletraOnboard\, so a new app version keeps every earlier run. Seven tables:

TableHolds

run_eventsevery event, in order

The application never imports SQLite. It sees the RunStore protocol in domain/ports.py; tests hand in a temporary database.

Settings and credentials

  • config.py loads Settings from the environment and .env (GreenLake client id and secret, token URL, proxy override). The coordinator re-reads them at every step, so credentials typed into the Prerequisites page take effect without a restart.
  • One array credential per run (ADR 0013): coordinator.array_credential() takes it from the sheet, the Provisioning tab's array admin first, else the DSCC system credential. Every step uses that one; the UI only learns whether one is present and from where.
  • One array address per run: the Initialisation tab's management address, else the Provisioning tab's host. The parser refuses a sheet where the two disagree. (Before this rule, verify and the as-built once reached two different arrays in the same run.)
  • Passwords are SecretStr; domain/policies.redact() and the command log strip them from anything that is stored or shown.

11. Why it is testable

703 tests run in about ten seconds with no lab. Two things make that possible.

  1. Factories. Every function that touches a device takes its client as a factory argument with a real default: array_cli_factory=make_array_cli, wsapi_factory=make_wsapi, vcenter_factory=make_vcenter, and for the step services provision_factory, cloudinit_factory, dscc_factory, verify_fn. Tests pass fakes. The developer "dev servers" that fake an array for UI work use the same seam.
  2. Captured output as fixtures. Parsers are pinned to real command output saved under tests/fixtures/ (rack13_fabric, rack13_wsapi, rc_pair, …), scrubbed of passwords and customer data. Device output never matches the documentation exactly, and these captures are how the tests know the truth.
The rule that follows A test never calls GreenLake, an array, vCenter or a switch. Something that needs the network is a lab script in lab/, run on a jump box, with its result attached to the pull request.

13. Facts that are easy to get wrong

  • GreenLake device assignment is two PATCH calls: application and region first, subscription second. One call with both is rejected.
  • In the service catalog the id is serviceManager.id (nested), not application_id; you filter on status but the response field is provisionStatus.
  • GreenLake writes return 202 + Location. Always poll.
  • DSCC region codes are not GreenLake region ids: ap-northeast is jp1, us-west is us1, eu-central is eu1, eu-west is uk1.
  • The array's setup page must be at https://169.254.…. A fail-prov-* error there is a GreenLake state problem (device or subscription), not a network one: fix GreenLake, do not retry the wizard.
  • The array's own host list (showhost -d) is the host truth. The fabric name server is zone-filtered and can show a peer array as if it were a host.
  • A host set export shows up in showvlun as a template row (hostname: set:<name>, active: false) plus one active row per member host and path. De-duplicate WWNs: FCPaths repeats a WWN once per array port.
  • Writing a zone to the switch's defined configuration is not activation. Only the verify step, which checks logins on both fabrics, opens the export gate.
  • The Remote Copy target carries one mode: six existing Sync groups on the lab pair mean a periodic group needs the groups paused or a second target.
  • Shipped .ps1 files must be pure ASCII; Windows PowerShell 5.1 reads them as ANSI.
  • paramiko is pinned below 4: version 4 dropped the old key exchange that FOS 7.x switches still require.

Glossary

Run
One array, one mode, one event history.
Mode
Which steps a run has; a preset over the step registry, or Custom.
Step service
A class in application/*/steps.py with one start_* per step, built on the RunCoordinator.
Event
A RunEvent: the record of what a step did, stored and streamed. The UI's only source of truth.
Artifact
A blob saved per run and kind: discovery report, as-built document, replication results.
Plan
What apply will do, object by object: create, exists, update, conflict. Held in memory until applied or invalidated.
Removal set
The commands that undo exactly what an apply created. Shown, never run.
Export gate
The hosts the zoning check confirmed on both fabrics; only they get exports.
Allowlist
The base commands the SSH clients will send. Anything else is refused before it leaves the process.
Console
Every device command of a run with its output (command_log), plus a read-only prompt.
Fixture
Real, scrubbed device output under tests/fixtures/ that a parser is pinned to.
WSAPI
The array's REST API, the only write path today, driven through python-3parclient.
RCIP, target, link, group
Remote Copy's three layers: the IP ports, the partnership between two arrays, and the replicated volume groups.
ADR, SPEC
A decision record in docs/adr/; a feature's requirements in docs/specs/. Both are for developers; neither appears on screen.
